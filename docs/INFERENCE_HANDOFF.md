# 推理加速交接

## 任务与边界（负责人已确认）

目标是让当前模拟座舱更快响应，优先关注用户说完后多久看到正确状态、多久真正听到第一声。保持 **Qwen2.5-Omni-3B、原始语音理解、当前工具协议与行为**。允许更换推理框架、量化、编译、缓存和流式实现；更换模型、引入独立TTS或将输入改成ASR串联需另行讨论。

数据集构建由负责人承担。本次不是委托训练新模型，也不是让加速工作线自行修改数据标签、工具接口或交互政策。具体绝对时延门槛尚未约定；先复现、定位，再提出可测的阶段目标，不能把建议数值当验收承诺。

## 当前代码究竟怎样运行

HF参考服务入口是 `server_omni25_opt/serve.py`，build `native3b-single-decision-v1-20261014`。双卡流式入口是 `scripts/run_vllm_streaming.sh`，build `native3b-vllm-streaming-v1`。

一次请求：浏览器16kHz WAV → 原始音频与状态/短历史进入Thinker → 一次输出动作+回复JSON → 本地执行器校验并更新模拟状态 → 页面收到状态和文字 → 同一个Omni根据最终文字生成声音。

**正常请求有两次模型运行：一次语义决策、一次语音生成。** 语音生成中的Thinker文字受约束。双卡服务把Token2Wav生成的音频块经NDJSON送到浏览器；HF参考服务发送完整音频。

核心位置：

- `single_call.py`：决策、完整JSON验证、工具执行、历史、request_id去重、回复放行；`build_decision_messages()`也是训练导出的入口。
- `small_model_eval/backend.py`：processor、音频处理、模型generate、Thinker输出token统计、强制朗读文字。
- `server_omni25_opt/native_backend.py`：Thinker/Talker/波形阶段计时。
- `server_omni25_opt/vllm_backend.py`：vLLM-Omni请求、逐字播报约束、音频分块与计时。
- `server_omni25_opt/qwen25_omni_3b_streaming.yaml`：两张GPU的三阶段分配、Talker编译与共享内存连接。
- `server_omni25_opt/rope_fix.py`：Transformers 5.8.0下Token2Wav旋转布局的进程内兼容修复。更换版本时先验证是否仍需要，不能直接删除后宣称音质无影响。
- `realtime_turn.py`：状态、文字、音频事件桥接。
- `web/stream-player.js`、`web/slai/voice-bridge.js`：播放调度、录音收尾、用户端时间。

## 已有测量及限制

2026-10-14，同一个已加载Qwen2.5-Omni-3B BF16模型、单H100 80GB、SDPA，旧/新路径交替处理同样的8条文字和3条合成音频，各一遍。

- 新路径11/11完成；旧路径10/11完成，越界例旧路径重试后报错。
- 更严格的基础检查两者都是7/11；新路径另外1条越界调用被程序拦住，不能算模型答对。
- 新路径仍有：复合范围漏后门；“不要开窗”却关闭车窗；查询温度却调用调温。还出现只开前门、回复却称所有门已开的不一致。
- 两者都通过基础检查的相同5个输入，整轮完成时间中位数旧2.73秒、新3.23秒；状态确定中位数旧0.60秒、新1.06秒。
- 非语音阶段输出token中位数，新43、旧分类与规划合计23。少一次推理并没有自动带来提速。

参考明细：`benchmarks/reference/baseline_20261014.jsonl` 和 `summary_20261014.json`。这是开发短测，不是正式benchmark：每题一次、回复长度不同，第一条音频未单独预热，新路径在该条先运行；没有浏览器/物理扬声器计时。旧失败请求没有声音，不能把其快速退出时间与成功出声混算性能。

### 双卡流式复测（2026-10-15）

同一份Qwen2.5-Omni-3B BF16权重，HF参考使用1张H100，vLLM-Omni使用2张H100，均在语音预热后对相同11条开发请求各运行一次。vLLM-Omni任务31781成功，11/11请求完成，基础检查7/11、状态和显式字段8/11，均与HF参考持平。双卡服务的状态确定中位数为0.884秒，首次音频到达2.085秒，整轮完成2.187秒；HF参考的状态确定为1.385秒，整轮完成4.038秒。11条语音共收到13个原生音频块，全部通过24 kHz单声道、序号递增、流出PCM与最终PCM一致性检查；实时`/turn-stream`接口的事件顺序也通过检查。

其中7条回复文字完全相同且音频时长相差不超过20%的请求，HF状态/整轮中位数为1.090/3.545秒，双卡为0.855/2.187秒，双卡首块为2.085秒。这个对照只能作为开发测量：两组使用的GPU数量、引擎及Transformers环境不同，每条仅测一次；没有p95、并发、浏览器实际播放或听感验收。短回复常只有一个音频块，较长回复才显示分块提前到达的收益。

保留四类基础检查失败。特别是“打开所有车门和前排车窗”在双卡路径生成了多余的JSON右括号，本地协议校验拒绝执行；HF参考虽然执行了动作，但漏掉后门，同样没有通过该用例。否定指令和温度查询仍会产生误操作，越界温度由协议拒绝。上线前应单独处理这些语义问题，不能把本次推理加速等同于车控质量验收。

本地复测产物为被忽略的`output/hf_baseline_20261014_230704/`和`output/vllm_smoke_20261014_235716/`，含逐条结果及WAV；作业日志在`output/jobs/31781-vehicle-patched-vllm-test-1014-235458417/`。回滚时按README启动HF参考服务，仍使用相同座舱协议。

## 建议优先排查顺序

1. **先建立分段计时。** 分开记录上传/排队、预处理与音频编码、prefill、决策decode、校验执行、语音文字约束、Talker、Token2Wav、网络与播放器缓冲。现有组件计时不能完整拆出预处理，且含用于测量的CUDA同步。
2. **解释新路径为何更慢。** 检查JSON输出token、提示词长度与重复编码；不能只看模型调用次数或tokens/s。控制实验固定内容与输出预算，单独报告精简提示词/缩短回复带来的变化。
3. **语音生成与播放。** 对双卡服务核对首块到达、分块顺序、音频连续性、截断与内容一致性，并测浏览器实际播放开始时间。
4. **引擎/精度/编译。** 可以比较更合适的执行引擎、量化、attention实现、算子和编译缓存；每种配置明确权重、精度、组件放置及内存，不能用另一个模型冒充同模型优化。
5. **历史和缓存。** 最近两轮可能带历史音频。可研究重复音频特征或不可变前缀缓存，但必须保持状态新鲜、会话隔离和真实上下文。不能缓存整句回答代替真实推理来报告模型速度。

## 应如何证明优化有效

先固定模型快照、同一输入集、初始状态、历史、硬件、输出上限、采样设置，再对照。区分冷启动、首次请求、预热请求；建议同组输入重复测量，累计至少约100次请求，报告样本量、p50/p95及失败率。这个数量是建议的起点，不是已经完成的测量。

必须同时报告：

- 服务端状态确定时间、首个真实音频块产生时间、整轮完成时间。
- 浏览器录音结束→状态更新、录音结束→实际播放开始；需要物理扬声器首声时再做声学测量，不能混用时钟口径。
- JSON合法率、完整状态正确率、无操作误调用、额外字段写入、回复与动作一致性。
- 音频自然度、内容遗漏/重复、截断、连续播放断裂；不能用“PCM非空”代替听评。
- GPU/CPU内存、并发条件、排队时长和计费/资源口径。

不要通过删除难例、吞掉失败、只计最快一次、缩短成无意义回复、偷偷回退模型、增加未披露的重试等方式制造加速。现有基线本身尚不可靠，优化既不能新增误操作，也不能把旧错误当作正确答案复制。
